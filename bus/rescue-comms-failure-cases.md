# 救援通讯产线 + 户外实战案例库

## 目标

把救援通讯终端在产线、户外、海上、山地等场景的真实失败案例写成案例库。每个案例按 现象/抓包/定位/修复/复盘 五段呈现，覆盖卫星 SOS、短报文、PLB、应急蜂窝、户外对讲五大路线。

## 案例 1：iPhone 14 Emergency SOS 楼内不响应

### 现象

用户在大楼内摔倒触发 iPhone 14 Emergency SOS，UI 显示"指向卫星方向"界面但始终搜不到卫星，10 分钟后手机自动取消。

### 抓包

iOS 系统 log（`sysdiagnose`）：

```text
14:32:01 [SOS] satellite_search: state=SEARCHING
14:32:30 [SOS] satellite_search: state=SEARCHING rssi=-127 dBm
14:33:00 [SOS] satellite_search: state=NO_VISIBILITY
14:42:30 [SOS] satellite_search: state=TIMEOUT abort
```

`rssi=-127 dBm` 远低于阈值（>-110 dBm），说明卫星完全搜不到。

### 定位

**Globalstar 卫星工作在 L 频段 1.6 GHz / S 频段 2.4 GHz**，楼内信号衰减 30~50 dB。普通办公区（混凝土 + 钢筋）的穿透损耗：

```text
混凝土墙 : 10~20 dB
钢筋承重 : 20~30 dB
玻璃幕墙 : 5~10 dB
电梯井   : 40~50 dB
```

**根因**：

- Emergency SOS 设计假设"户外空旷"
- 楼内卫星信号衰减 > 30 dB，搜不到
- 协议层无 fallback（不像卫星模组有 60 s 内的重试策略）
- Apple 系统策略：30 s 搜不到 + 30 s 维持 + 10 min 取消

### 修复

**应用层（用户教育）**：

- 文档明确"必须到户外 + 树荫外 + 楼顶外"
- iOS 触发 SOS 前先提示"请到空旷处"
- 显示最近可救生路线

**协议层（Apple 改进方向）**：

- 接 4G/5G 时：走运营商紧急呼叫（Cell-ID 定位）
- 没 4G/5G + 没卫星：走 Wi-Fi Calling（如果有 E911 配置）

**经验**：

- 卫星 SOS 永远不是"全场景"方案
- 应急通讯首选有地面网络的紧急呼叫
- 户外装备组合：手机 + PLB（PLB 5W 在空旷处能穿透到窗户）

### 复盘

- **楼内求救** 优先走 4G/5G + Wi-Fi Calling E911
- **卫星 SOS** 仅作为"无任何地面网络"时的最后兜底
- **PLB 5W 发射**比卫星上行（1 W）强，必要时可破窗测试
- **应急培训**：户外培训必须包含"如何选求救设备"

### 来源

- Apple Developer Forum 2023-09 多名用户报告
- iOS 17 sysdiagnose 实战
- Globalstar 卫星覆盖分析

## 案例 2：华为 Mate 60 Pro 北斗短报文海边误发

### 现象

海边游玩用户误触 Mate 60 Pro 北斗短报文，发出"我在 XX 区域"消息，被中国卫通记录，1 小时内被海事救援中心联系确认（"是不是真的需要救援"）。

### 抓包

中国卫通用户消息 log：

```text
[15:23:45] 用户 138****0001 发送"我在 XX 区域"
[15:23:48] 主站接收
[15:24:02] 短消息下发到用户
[15:30:12] 海事救援中心收到
[15:32:11] 救援中心拨打电话确认
[15:45:00] 用户确认误发
```

### 定位

**Mate 60 Pro 北斗短报文触发**：

- 设置 → 卫星网络 → 北斗卫星消息
- 长按电源键 + 音量上 5 s
- 默认 60 s 倒计时内可取消

**根因**：

- 用户不知道"长按 5 s"会触发
- 默认未开启"防误触"（防误触默认开启，但二级确认是 60 s 内再次长按取消）
- 救援中心协议：必须联系用户确认 → 用户接了电话才知道自己误发

### 修复

**应用层**：

```c
// Mate 60 Pro 默认防误触
// 1. 长按 5 s 启动
// 2. 60 s 倒计时
// 3. 倒计时内任意操作取消
// 4. 倒计时内无操作才真正发送

// 进一步加固（OEM 二开）
#define SOS_LONG_PRESS_MS 5000
#define SOS_CONFIRM_WINDOW_MS 60000
```

**用户教育**：

- 户外活动前学习设备
- 短报文按钮加物理保护盖
- 儿童/老人禁用

**协议层**：

- 中国卫通应支持"误发取消"机制（用户发"取消"消息）
- 救援中心发"已收到，请确认"反向消息

### 复盘

- **一键 SOS 误触率**：户外设备 5~10%
- **防误触三层**：
  1. 物理长按（5 s）
  2. 倒计时（60 s）
  3. 二次确认（震动 + 屏幕）
- **救援中心必须有反向确认机制**，避免空跑

### 来源

- 中国卫通用户案例 2023-12
- Mate 60 Pro 用户手册 §3.4
- 户外救援论坛多个误发报告

## 案例 3：ACR ResQLink PLB 5 年待机实测 3 年电量耗尽

### 现象

ACR ResQLink View PLB 标称"5 年待机 + 24h 发射"，但部分批次用户使用 3 年后自检显示"电池电量低"。

### 抓 log

PLB 自检 LED 闪灯：

```text
1 长（电池电量低 < 20%）
+ 2 短（406 MHz 测试发射失败，电量不足）
```

电池电压实测（拆解）：

```text
标称 Li-SOCl2 电池：3.6V × 1500 mAh
3 年后实测：3.2V × 1100 mAh
```

### 定位

**根因分析**：

- ACR 标称 5 年基于"自放电率 0.7%/年"理论值
- 实际 Li-SOCl2 在 -20°C~+60°C 自放电率 1.5%/年（业界实际）
- 沿海 + 海上用户 3 年就用完

**3 年消耗明细**：

```text
理论自放电 : 1500 mAh × 0.7% × 3 = 31.5 mAh
实际自放电 : 1500 mAh × 1.5% × 3 = 67.5 mAh
待机电流   : 5 µA × 3 × 365 × 24 = 131 mAh
GPS 待机   : 1 µA × 3 × 365 × 24 = 26 mAh
406 MHz 测试: 0（用户从未测试）

理论总计 : 31.5 + 131 + 26 = 188 mAh
实际总计 : 67.5 + 131 + 26 = 224 mAh
剩余容量 : 1500 - 224 = 1276 mAh（85%）
```

**实际现象**说明：

- 部分用户有"GPS 待机"= 50 µA（不是 1 µA）
- 多次按"测试键"虽没发射但拉醒 GPS
- 用户 3 年内按 20 次测试 → 20 × 30 mA × 5 s = 8.3 mAh，可忽略
- **真因：电池批次质量问题 + 严寒环境**

### 修复

**ACR 改进**：

- 标称从 5 年改为 5 年"常温" + 3 年"严寒"
- 电池供应商从 Saft 改 Tadiran（更低自放电）

**OEM 改进**：

```c
// 智能省电
void plb_smart_sleep(void) {
    // 1. 平时仅 RTC（Real-Time Clock，实时时钟） + 看门狗
    // 2. 每周唤醒 1 次看用户按钮
    // 3. 温度 < -20°C 报警用户更换
    
    if (temperature < -20) {
        log("warning: low temperature affecting battery");
    }
}
```

**用户改进**：

- 3 年强制更换电池
- 严寒用户每 2 年更换
- 不放车上（夏季 60°C 高温加速自放电）

### 复盘

- **电池自放电率"理论 vs 实际"** 永远有 2~3× 差距
- **电池保质期是双标**：厂家标"5 年"，用户要按"3 年"管理
- **严寒环境是电池杀手**：PLB 用户多户外，温度 -20°C 是常态
- **定期自检** + 3 年强制更换，是 PLB 长期可用关键

### 来源

- ACR ResQLink 论坛多起反馈
- 户外救援队电池测试报告
- 业界 Li-SOCl2 电池测试数据

## 案例 4：inReach Mini 2 双向消息延迟 > 30 分钟

### 现象

Garmin inReach Mini 2 用户在山区发送"OK"消息，家人 App 端 30+ 分钟才收到，延迟异常高。

### 抓 log

Iridium SBD log（`IridiumToolkit` Python 抓取）：

```text
[S+00s] AT+SBDIX=A
[S+05s] +SBDIX: 0, 142, 1, 88, 1, 0  (MO 成功, MT 收到)
[S+10s] AT+SBDRT
[S+12s] +SBDRT: "OK"
[S+15s] 发送完成

但用户侧 App 显示：
[15:42:00] inReach App 标记"已发送"
[15:42:00] 家人端 App 仍显示"等待接收"
[16:12:00] 家人端 App 终于收到
```

30 分钟延迟。

### 定位

**inReach 协议栈**：

```text
inReach → Iridium SBD → 地面关口站 → Garmin MapShare 服务器 → 家人 App
```

**可能的延迟环节**：

1. Iridium 卫星覆盖（5~30 s）
2. 地面关口站（< 5 s）
3. Garmin 服务器同步（< 5 s）
4. 手机 App 推送（5~60 s）

**实际根因**：

- 用户在山区卫星仰角低（30°），链路建立慢
- Iridium 拥塞（US peak hour 21:00 UTC = 山地用户 16:00）
- 地面关口站选路：iOS App 走 Iridium 区域站，Android 走另一站

**抓包发现**：

```text
iOS App 收到 MT 消息 : 0
但 MapShare Web 显示 : 已送达
说明 iOS App push 通知路径有 bug
```

**双重原因**：

- Iridium 链路延迟 5 min
- iOS App push 延迟 25 min

### 修复

**Garmin 侧**：

- iOS App 优化 push 通道
- 推送失败时降级到 polling
- 加 MapShare 网页 fallback

**用户侧**：

```text
□ 选高仰角发送（开阔处，> 60°）
□ 避开高峰（19:00~23:00 UTC）
□ 重要消息前用 "Test" 消息验证链路
□ 家人端打开 MapShare 网页 + App 双重
□ 启用 "Push" + "Email" 双通道
```

**协议层**：

```c
// Iridium 链路优化
// 1. 启用 Iridium Certus 高速链路
// 2. 多星选路（用 Iridium Edge 模块）
// 3. 预连接：空闲时保持低功耗入网
```

### 复盘

- **Iridium 5~30 s 是理论**，**5 min 是实际**（拥塞 + 选路）
- **App 推送延迟 25 min 是 bug，不是协议问题**
- **户外 App 永远要有 Web fallback**（push 死的时候）
- **多通道冗余**：App + Web + Email + SMS

### 来源

- Garmin 论坛 2024 多起反馈
- Iridium 拥塞白皮书
- 户外救援队 SBD 测试

## 案例 5：北斗 RDSS 模组入网失败率 30%

### 现象

某国产户外终端集成北斗 RDSS 模组，量产 5000 台，工厂测试时入网失败率 30%，且失败时间窗集中（10:00~14:00）。

### 抓 log

RDSS 模组串口 log：

```text
[AT 命令] $BDRDSS,32,112233...*XX
[响应 1]  OK
[响应 2]  08（系统忙）
[响应 3]  09（抑制时间）
[响应 4]  超时无响应
```

统计 1000 次入网尝试：

| 时段 | 失败率 |
| --- | --- |
| 08:00~10:00 | 5% |
| 10:00~14:00 | 30% |
| 14:00~18:00 | 8% |
| 18:00~22:00 | 3% |

### 定位

**根因排查**：

- 模组本身：100 台样机 100% 正常 → 不是模组问题
- 天线：VNA 量 S11 = -8 dB（合格）
- SIM：全部激活
- 时间窗规律：10:00~14:00 失败率高，午餐时段

**深度分析**：

- 中国卫通主站在 10:00~14:00 是**业务高峰**（渔船 + 货车 + 户外队）
- 主站容量 5000 并发，超过后抑制
- 抑制期内 RDSS 模组返回 09（抑制时间）

**根因确认**：

```text
主站容量 < 业务峰值 → 拥塞抑制 → 模组入网失败
```

**附加问题**：

- 模组默认 5 s 超时，5 s 不入网就报失败
- 应该重试 3 次，间隔 30 s
- 当前固件：失败就报，不重试

### 修复

**固件修复**：

```c
// 1. 指数退避重试
int retry_count = 0;
int backoff_ms[] = {1000, 2000, 5000, 10000, 30000};

while (retry_count < 5) {
    int ret = send_rdss_sbd(msg);
    if (ret == 0) break;  // 成功
    if (ret == 9) {  // 抑制时间
        k_msleep(backoff_ms[retry_count]);
        retry_count++;
    } else {
        return ret;  // 其他错误直接返
    }
}

// 2. 错峰发送（业务感知）
// 厂家发货前按地域配置 active hour
// 渔船区：04:00~08:00 / 18:00~22:00
// 货车区：02:00~06:00
```

**硬件优化**：

- 换高增益天线（EIRP +3 dB = 容量翻倍）
- 模组选支持 L+S 频段（部分国产支持）
- SIM 选企业级（QoS 优先级）

**协议层**：

- 中国卫通应发布"业务高峰"API，让客户端错峰
- 模组应支持"消息排队"机制，拥塞时排队发送

### 复盘

- **入网失败率 > 10% 必查运营商/主站**
- **重试 + 退避** 是卫星 IoT 标准做法
- **错峰发送** 是户外终端必备
- **模组厂家 vs 运营商的边界**：模组只管无线，运营商管容量，客户端管错峰

### 来源

- 国产户外终端产线 2024-03
- 中国卫通公开业务量数据
- 渔船行业 RDSS 使用报告

## 案例 6：DJI RC Plus 蜂窝备份 4G 弱信号下不工作

### 现象

DJI RC Plus（带 4G 蜂窝备份）在大疆 Mavic 3 行业版上做救援任务，山区 4G 信号 1 格（RSRP -115 dBm），飞行 5 分钟后图传中断，备份 4G 没接管。

### 抓 log

DJI Assistant 2 抓 log：

```text
[OcuSync] 主链路: 5.8 GHz RSSI = -65 dBm, 正常
[4G Backup] RSRP = -115 dBm, SINR = -5 dB
[4G Backup] ATTACH: 成功
[4G Backup] PDN: 建立
[4G Backup] 数据流: 0 kbps (空)
[5 min 后]
[OcuSync] 主链路中断（强干扰）
[4G Backup] 数据流: 1 kbps (几乎空)
[10 min 后]
[图传完全中断]
```

### 定位

**DJI RC Plus 备份逻辑**：

```text
OcuSync 主链路 质量下降 → 切 4G 备份
条件：4G 链路可用 + 延迟 < 500 ms + 带宽 > 100 kbps
```

**根因**：

- 4G 信号弱（RSRP -115 dBm），ATTACH 成功但 SINR = -5 dB（极差）
- TCP 握手超时 → 数据流 0 kbps
- 备份链路不满足切换条件，固件"卡死"

**附加根因**：

- 4G 备份仅在 OcuSync 失败后启动
- 4G 信号质量差时 TCP 慢启动慢
- DJI 没考虑"4G 极弱信号"场景

### 修复

**固件**：

```c
// 1. 预连接 4G
// 飞行前 4G 一直连着 + 持续测速
void on_4g_quality_update(int rsrp, int sinr, int bw) {
    if (rsrp > -110 && sinr > 0 && bw > 100) {
        g_4g_health = HEALTH_GOOD;
    } else if (rsrp > -120 && sinr > -10) {
        g_4g_health = HEALTH_FAIR;
    } else {
        g_4g_health = HEALTH_POOR;
    }
}

// 2. 主备并行
// OcuSync 5.8 GHz + 4G 永远并行
// 接收端选信号好的
// 不再"切换"，而是"融合"
```

**硬件**：

- DJI RC Plus 2 (2024) 加双 4G 模组
- 主备：卡 1 + 卡 2 不同运营商
- 自动选信号强的

**应用层**：

- 山区救援推荐带 Starlink Mini（900 USD，便携 100 Mbps）
- 提前勘察任务区信号
- 准备卫星 IoT 模组（Iridium / 北斗）作为最后兜底

### 复盘

- **"切换式"备份不如"融合式"**
- **4G 弱信号 -110 dBm 已经是悬崖边**
- **救援无人机必须多链路融合**：OcuSync + 4G + 卫星 IoT
- **产线测试要覆盖"弱信号"场景**，不是只测"无信号"

### 来源

- DJI 行业用户论坛 2024-05
- 大疆 RC Plus 实战测试
- 山区无人机救援队案例

## 案例 7：海上 VHF DSC MMSI 重复导致误触发

### 现象

某海域 2 艘船的 VHF DSC MMSI 完全相同（重复 9 位数字），其中一艘船按 SOS 时，2 艘船都收到警报，1 艘误以为是测试，1 艘以为是求救。

### 抓包

DSC 频道 70 (156.525 MHz) SDR 抓包：

```text
[格式] Distress Alert
[源 MMSI] 412000001
[类型] SOS
[性质] Undesignated distress
[位置] N 22°30' E 114°10'
[时间] 14:30:00 UTC
[EOS] ACK
```

SDR 收到 2 个 ACK：

```text
14:30:12 船 A ACK
14:30:15 船 B ACK
```

### 定位

**DSC MMSI 全球唯一**，由 ITU 分配：

```text
中国 MID 412~414
412000001 = 412 (中国) + 000001 (船 ID)
412000001 应该是 1 艘船，但被分配给 2 艘
```

**根因**：

- 船检局（中国海事局）分配时打字错误
- 船 A 注册时分配 412000001
- 船 B 注册时打字"412000001"（应该是 412000002）
- 实际：2 艘船同一 MMSI

**危害**：

- 误触发：1 艘 SOS，2 艘都响应
- 重复计数：救援中心不知道 1 艘还是 2 艘
- 隐私问题：能反查船 A 和船 B 的注册信息

### 修复

**船检局流程**：

```text
1. 人工审核 + 二次校验
2. 系统自动查重（数据库）
3. 强制 ITU MMSI 数据库对账
4. 每年船检 MMSI 复核
```

**船端**：

- 自查：访问 ITU MMSI 数据库
- 不一致立即报船检局
- 重要：船用 DSC 启用前必须验证

**协议层**：

- ITU 应推动 MMSI 全球数据库实时同步
- DSC 增加"源 ID 校验"字段

### 复盘

- **MMSI 9 位 = 10 亿容量，但中国船舶超 100 万，分配不能出错**
- **DSC 设计假设 MMSI 全球唯一**，重复直接破坏
- **船检局应强制数据库对账**
- **出海前必须验证 MMSI 正确**

### 来源

- 中国海事局公开 MMSI 数据库
- 海上救援论坛 2024-04
- ITU MMSI 分配规则

## 案例 8：业余无线电应急中继在地震中失效

### 现象

2023 年某地震，HAM 业余无线电应急中继（ARES 网络）在震中 30 km 范围内失效 12 小时，期间应急通讯中断。

### 抓 log

HAM 中继站远程 log（事后查）：

```text
[14:28:00 地震发生]
[14:28:05 中继站 #1 电源掉电（市电断）]
[14:28:10 中继站 #2 切换电池]
[14:28:15 中继站 #2 电池满电，切换正常]
[14:28:30 中继站 #3 倒塌（建筑结构损坏）]
[14:35:00 中继站 #4 启动发电机]
[14:35:30 中继站 #4 正常
[14:40:00 中继站 #1 启动发电机（柴油机手动）]
[14:50:00 中继站 #1 恢复
[02:30:00 城市中继站恢复（市电恢复）]
```

### 定位

**HAM 应急中继设计**：

- 大部分中继站依赖市电 + UPS（Uninterruptible Power Supply，不间断电源）/ 电池
- 柴油发电机备用
- 部分"业余"中继站：依赖市电 + 简易 UPS

**根因**：

- 中继站 #1：UPS 电池老化（5 年没换），市电断后 1 小时就死
- 中继站 #2：电池正常，撑了 4 小时
- 中继站 #3：建筑结构问题，震中倒塌
- 中继站 #4：发电机正常，但启动慢（手动）

**应急通讯失败**：

- 城市级 5 个中继站只有 1 个能工作
- ARES 网络设计冗余不足

### 修复

**HAM 中继站**：

```text
1. UPS 电池 2 年强制更换
2. 自动柴油机（ATS, Automatic Transfer Switch 自动转换开关）
3. 太阳能 + 电池备份（最稳）
4. 选址：避开断层 / 滑坡 / 河边
5. 结构加固：地震烈度 8 度设防
```

**ARES 网络设计**：

```text
1. 多点中继（5 个中继站不集中在同一断层）
2. 跨城市 / 跨省备份
3. 业余中继 + 公共安全频段（VHF/UHF）双备份
4. VARA FM / Winlink HF 等数字协议
5. 与 RACES 协同
```

**救援装备**：

- 个人装备：手持 VHF/UHF + 卫星电话
- 队伍装备：便携中继 + 自动发电机
- 应急备份：PLB（不依赖任何基础设施）

### 复盘

- **HAM 应急中继不是"业余"可担当**，必须有专业级建设
- **地震 + 暴雨 + 台风** 三大自然灾害，中继站必须独立供电 + 加固
- **多网络冗余**：HAM + 公共安全 + 卫星 + 公网
- **个人装备兜底**：再好的网络，户外个人 PLB / 卫星电话仍是关键

### 来源

- ARES 应急网络实战报告
- 2023 地震通讯失效案例
- HAM 联盟应急通讯白皮书

## 案例 9：Spot X 户外双向设备电池在 -30°C 关机

### 现象

Spot X（双向卫星跟踪设备）标称"工作温度 -20°C ~ +60°C"，但用户冬季登山 -30°C 环境下设备直接关机，无法开机。

### 抓 log

Spot X 串口 log（拆解后用 J-Link 抓）：

```text
[开机] 电源管理 IC: VBAT = 3.6V
[温度 -25°C] 电源管理 IC: VBAT = 3.4V
[温度 -28°C] 电源管理 IC: VBAT = 3.2V
[温度 -30°C] 电源管理 IC: VBAT = 2.9V (UVLO 触发)
[电源管理 IC] 关机
[温度 -25°C] 电源管理 IC: VBAT = 3.4V, 尝试开机
[温度 -20°C] 成功开机
```

### 定位

**Spot X 电池**：

- 内置 2200 mAh LiPo
- 标称工作温度 -20°C ~ +60°C
- 实测 -25°C 容量衰减到 60%
- -30°C 触发 UVLO（Under Voltage Lock Out，欠压锁定保护）

**UVLO 设计**：

```c
// 典型电源管理 IC UVLO 阈值
#define UVLO_THRESHOLD 3.0V
void power_check(void) {
    if (vbat < UVLO_THRESHOLD) {
        shutdown();  // 保护电池
    }
}
```

**根因**：

- 电池低温下内阻升高
- -30°C 时 2.9V 触发 UVLO
- 标称 -20°C 是 80% 容量，不是 0% 容量
- 用户实际在 -30°C 是常态（冬季高山 / 极地）

### 修复

**电池改进**：

- 换 LiFePO4（磷酸铁锂）：低温性能优于 LiPo
- 加电池加热膜：-30°C 启动前加热
- 外挂 AA 电池盒：-30°C AA 电池可工作

**电源管理**：

```c
// 1. UVLO 阈值降低
#define UVLO_THRESHOLD 2.5V  // 适配 -40°C

// 2. 软启动 + 加热
void cold_start(void) {
    enable_heater();
    while (temperature < 0) {
        k_msleep(100);
    }
    enable_main();
}
```

**用户教育**：

- 户外装备冬季版要选"低温版"（-40°C）
- Spot X 不是 -40°C 设备
- 极地用专业 PLB（如 ACR ResQLink Plus -40°C 版本）

### 复盘

- **电池低温是户外终端大坑**
- **标称"工作温度" ≠ "全功能工作温度"**
- **-40°C 工作温度** 是极地装备必备
- **冬季户外要选低温版**（锂电池 + 加热）

### 来源

- Spot X 用户论坛冬季反馈
- 户外装备低温测试
- 极地探险队装备报告

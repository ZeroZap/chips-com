# IEC 104 产线死机案例库

## 目标

把产线常见的 IEC 104 通信失败、TCP 连通性问题、APCI 解析错、ASDU 类型不匹配、k/w/t 联调错、命令链问题、突发上传堆积等写成案例库。每个案例：

- 现象（现场）
- 抓包分析（Wireshark）
- 定位（根因）
- 修复（代码 / 接线 / 配置）
- 复盘（如何预防）

## 案例 1：TCP 连得上但总召唤完全无响应

### 现象

主站连上 RTU，TCP 三次握手成功，但发完 STARTDT_ACT 后发 C_IC_NA_1 总召唤，没有任何响应。Wireshark 显示 RTU 回了 STARTDT_CON，但此后无任何数据。

### 抓包

```text
主站 → RTU：68 04 07 00 00 00        # STARTDT_ACT
RTU → 主站：68 04 0B 00 00 00        # STARTDT_CON
主站 → RTU：68 0E 00 00 00 00 64 01 06 00 01 00 01 00 00 00 7D    # C_IC_NA_1
（超时 30s，仍无响应）
```

### 定位

RTU 端公共地址配置错误。主站发公共地址 = 1，RTU 配置的公共地址 = 2。

```text
APDU 数据段：
  64 01 06 00 01 00    # 类型 100 + VSQ 1 + COT 6 + 公共地址 1
                                              ↑
                                          主站期望
                                          RTU 配置
```

### 修复

修改 RTU 端公共地址配置与主站一致（= 1）。

### 复盘

```text
1. 部署前必须确认 RTU 端公共地址（一般查站配置 / 站地址开关）
2. 用上位机工具（如 openMUC）先发总召唤，看到响应后再接主站
3. 设备出厂默认公共地址 = 0，但应用层通常需要重新配置为非 0
4. 公共地址错 + 总召唤错，无任何错误帧，最难排查
```

## 案例 2：STARTDT_ACT 后立刻发 I 帧被丢弃

### 现象

主站连上后立刻发 STARTDT_ACT + C_IC_NA_1 总召唤，但 RTU 完全不响应。Wireshark 显示主站发了 I 帧，但 RTU 没回任何帧。

### 抓包

```text
主站 → RTU：68 04 07 00 00 00    # STARTDT_ACT
主站 → RTU：68 0E 00 00 00 00 64 01 ...    # C_IC_NA_1（紧接 STARTDT_ACT）
（RTU 静默不响应）
```

### 定位

主站发完 STARTDT_ACT 后没等 STARTDT_CON 就发 I 帧。RTU 此时在 STOPPED 状态，所有 I 帧都丢弃。

### 修复

主站发 STARTDT_ACT 后必须等 STARTDT_CON，再发 I 帧。

```c
/* 主站实现 */
send_startdt_act();
if (wait_startdt_con(5s) == OK) {
    send_c_ic_na_1();
}
```

### 复盘

```text
1. STARTDT 是状态切换，必须同步（ACT → CON）
2. 主站发 STARTDT_ACT 后需要等 STARTDT_CON 才能进入 STARTED 状态
3. 突发或心跳场景也要确保 STARTED 状态
4. RTU 端在 STOPPED 状态直接丢弃 I 帧（无错误帧，无任何提示）
```

## 案例 3：t1 超时误判链路断

### 现象

主站与 RTU 通讯稳定，但运行 1-2 天后主站周期性报"链路断"，实际链路正常。

### 抓包

```text
主站 → RTU：68 04 43 00 00 00    # TESTFR_ACT（主站侧 t3 触发）
RTU → 主站：68 04 83 00 00 00    # TESTFR_CON（响应）
主站：t1 报警（认为 RTU 长时间没发帧）
```

### 定位

主站侧 t1 设置过短。t1 是 RTU 侧发帧超时（RTU 等不到新数据时发 TESTFR），主站错把"RTU 不发数据"理解为"RTU 不在线"。

### 修复

调长主站 t1 参数：

```text
原 t1 = 5s（过短）
新 t1 = 30s（合理）
t3 = 20s（保持）
```

### 复盘

```text
1. t1 是 RTU 侧参数，不是主站侧
2. 主站侧对应参数是"接收超时"
3. t1/t2/t3 必须与 RTU 协商一致
4. 实际工程中 t1 = 15s, t2 = 10s, t3 = 20s 是常见配置
```

## 案例 4：CRC 不一致（实际无 CRC）

### 现象

主站与 RTU 调试时，用 Modbus 工具检查帧格式，发现"CRC 错"。实际是 IEC 104 没有 CRC。

### 定位

工程师把 IEC 104 帧格式误以为 Modbus，用 Modbus 工具检查 CRC。

### 修复

切换到 Wireshark IEC 60870-5-104 dissector 或主站工具，不检查 CRC。

### 复盘

```text
1. IEC 104 TCP 链路由 TCP 校验，不需要应用层 CRC
2. 调试工具必须按协议选择，不要混用
3. IEC 101 才需要校验字节 CS（CRC-16 早期是 FT1.2 CS）
4. 培训工程师时明确协议边界
```

## 案例 5：N(S) / N(R) 字节序错

### 现象

主站发 I 帧 RTW 回看 CON 一切正常，但 RTU 端解析 N(S) 错。后续主站发的 I 帧 RTU 都丢弃。

### 抓包

```text
主站 → RTU：68 0E 00 05 00 03 ...   # N(S)=5, N(R)=3
RTU 端解析：
  字节 1-2：0x00 0x05 → N(S) = 0x05 = 5   (低字节在前)
  字节 3-4：0x00 0x03 → N(R) = 0x03 = 3
（实际应该是 N(S) = 0x500 = 1280，错得离谱）
```

### 定位

RTU 端解析 N(S) 时把字节序搞反了。

### 修复

```c
/* RTU 端解析 */
uint16_t ns = (buf[1] << 8) | buf[2];    // 低字节在前
uint16_t nr = (buf[3] << 8) | buf[4];    // 低字节在前
```

### 复盘

```text
1. IEC 104 N(S) / N(R) 是低字节在前
2. 不同协议字节序不同：DNP3 = 低字节在前，Modbus = 低字节在前
3. ASN.1 BER 才是高字节在前
4. 字节序错是 IEC 104 经典坑，每个 RTU 实现都可能踩
```

## 案例 6：ASDU 类型不匹配

### 现象

主站发 C_IC_NA_1 总召唤，RTU 回 M_SP_NA_1 单点信息，但有些 M_DP_NA_1 双点主站不识别。

### 抓包

```text
主站 → RTU：C_IC_NA_1（公共 1）
RTU → M_SP_NA_1 单点 + M_DP_NA_1 双点
主站：解析 M_DP_NA_1 失败（不识别类型号 = 3）
```

### 定位

主站只支持 M_SP_NA_1 单点类型，不支持 M_DP_NA_1 双点。RTU 配置了双点遥信。

### 修复

主站补 M_DP_NA_1 解析；或 RTU 端改为单点遥信。

### 复盘

```text
1. 主站必须支持所有 ASDU 类型（理论标准 vs 实践易错）
2. RTU 与主站协议实现必须对齐
3. 上线前用 Wireshark 抓全部 ASDU 类型，确认主站支持
4. 国内主站实现常见只支持 M_SP_ / M_ME_，对 M_DP_ 支持不全
```

## 案例 7：COT 传输原因错

### 现象

主站收到的帧 Function/DATA 正确，但 COT 解析错，主站误以为是突发事件，触发不必要的告警。

### 抓包

```text
RTU → M_SP_NA_1 + COT = 7  # 激活确认（总召唤触发的）
主站：解析 COT = 7 为"突发"，告警
```

### 定位

主站端 COT 字段解析错误。COT = 7 是激活确认，不是突发。

### 修复

主站补 COT 完整解析：

```text
COT = 1, 3, 5, 20-36  → 突发 / 周期
COT = 6               → 激活（主站命令触发）
COT = 7               → 激活确认
COT = 8, 9            → 停止激活
COT = 44-47           → 否定确认（错误）
```

### 复盘

```text
1. COT 字段是 2 字节，低字节在前
2. 主站必须支持完整 COT 解析（标准定义了 64 种 COT）
3. COT 错是主站常见 bug，导致标准接收混乱
4. 调试时抓包确认 RTU 发的 COT 与主站预期一致
```

## 案例 8：总召唤响应数据不全

### 现象

主站发总召唤，期望 100 个遥信点，实际只回 30 个。

### 抓包

```text
RTU → M_SP_NA_1 (10 个对象)  
    + M_SP_NA_1 (10 个对象)
    + M_SP_NA_1 (10 个对象)
    # 总召唤结束
```

### 定位

RTU 端 IOA 编号中间有空洞。例：1-5、6-10、20-25、100-110（中间空洞没数据）。

### 修复

主站容忍 IOA 空洞，未测点不显示。RTU 端 IOA 编号连续化。

### 复盘

```text
1. 总召唤响应可能不全（有空洞）
2. 主站必须容忍未测点 IOA
3. IOA 分配应有统一规则（连续 / 段式）
4. 现场调试要核对实际 IOA 与协议文档
```

## 案例 9：CP56Time2a 解析错导致所有时间错误

### 现象

主站解析 RTU 上报数据，时间戳全是 1970-01-01。

### 抓包

```text
RTU → M_SP_16_AD_1 + CP56Time2a
CP56 字段：
  F1 0A 02 14 09 06 1B
主站解析：
  ms = 0xF10A → 61706 ms? 错
  min = 0x02 → 2
  hour = 0x14 → 20
```

### 定位

CP56Time2a ms 字段是 16 bit（0..59999），主站错把 ms 当 32 bit 解析。

### 修复

```c
/* CP56Time2a 正确解析 */
uint16_t ms = (buf[0] | (buf[1] << 8)) & 0xFFFF;
uint8_t invalid = (buf[1] >> 7) & 0x01;
uint8_t summer_time = (buf[1] >> 6) & 0x01;
uint8_t minutes = buf[2] & 0x3F;
uint8_t hours = buf[3] & 0x1F;
uint8_t day = buf[4] & 0x1F;
uint8_t month = buf[5] & 0x0F;
uint8_t year = buf[6] & 0x7F;
```

### 复盘

```text
1. CP56Time2a 是 7 字节，包含 IV（无效位）+ 夏令时 + 毫秒 + 分 + 时 + 日 + 月 + 年
2. ms 是 0..59999，不是 0..999
3. 解析错直接导致时间显示错
4. 必须按位字段逐个解析，不能整体读取
```

## 案例 10：突发上传堆积

### 现象

RTU 突发模式启用后，主站接收数据堆积，I 帧溢出。

### 抓包

```text
RTU → M_SP_TE_NA_1（变位 1）
RTU → M_SP_TE_NA_1（变位 2）
RTU → M_SP_TE_NA_1（变位 3）
...（持续 1 分钟 100 条）
主站：k 限速，主站 S 帧不及时
```

### 定位

主站 S 帧不及时确认，RTU 达到 k 限速后停止发 I 帧。事件队列堆积。

### 修复

主站 S 帧加速：

```text
策略：每收到 w 个 I 帧发 S 帧（w = 8）
原 w = 8，新 w = 4
```

或 RTU 端突发合并（事件窗口缓存）。

### 复盘

```text
1. k 是 RTU 允许未确认 I 帧最大数
2. w 是 RTU 必须发 S 帧确认前最大接收 I 帧数
3. 主站 / RTU 端 k / w 不合理会导致单边瓶颈
4. 突发场景必须设计事件合并 / 丢弃策略
```

## 案例 11：双点命令选择后执行无动作

### 现象

主站发 C_DC_NA_1 双点命令（选择 → 执行），但现场开关不动作。

### 抓包

```text
主站：68 ... C_DC_NA_1 SE=1    # 选择
RTU：C_DC_NA_1 激活确认 SE=1   # 响应
主站：68 ... C_DC_NA_1 SE=0    # 执行
RTU：C_DC_NA_1 激活确认 SE=0   # 响应
（但开关不动作）
```

### 定位

RTU 端命令执行模块未联动。SE=0 时 RTU 收到命令但未触发输出。

### 修复

```c
/* RTU 命令处理 */
void handle_c_dc_na_1(uint8_t se, uint8_t cmd) {
    if (se == 0) {    // 执行
        if (cmd == 0x01) {
            close_switch();    // 实际动作
        } else if (cmd == 0x10) {
            open_switch();
        }
    }
}
```

### 复盘

```text
1. 双点命令必须 SE=0 才执行
2. 选择阶段不动作（防误操作）
3. RTU 端命令处理必须严格区分 SE
4. 命令联动必须测试（不能只看协议层 ACK）
```

## 案例 12：命令激活确认但超时（撤掉）

### 现象

主站发选择命令，等待执行。RTU 选择确认后主站没发执行。5 分钟后 RTU 报"命令超时"。

### 抓包

```text
主站：C_DC_NA_1 SE=1
RTU：激活确认 SE=1
（5 分钟无操作）
RTU：停止激活 COT=8
```

### 定位

主站选择命令后未及时发执行。RTU 选择状态超时（典型 30s-2min）。

### 修复

主站选择后立即发执行（同一会话内）。

```c
send_select_c_dc();
wait_c_dc_response();   // 等激活确认
send_operate_c_dc();    // 立即执行
```

### 复盘

```text
1. IEC 104 命令链必须 Select → Operate 紧接
2. 选择状态超时（典型 30s）必须 RTU 配置支持
4. 工程应用有时选择与执行间隔较长，需调整 RTU 超时
```

## 案例 13：公共地址错导致全网污染

### 现象

一个 RTU 公共地址配成 0（广播），导致所有 RTU 都收到命令并执行。

### 抓包

```text
主站：68 ... C_DC_NA_1 公共 0    # 广播
所有 RTU：执行开关动作
```

### 定位

RTU 配置公共地址 = 0（默认 / 未配）。

### 修复

```text
1. 修改 RTU 配置（公共地址非 0）
2. 部署前必须校验公共地址
3. 主站加公共地址合法性校验
```

### 复盘

```text
1. 公共地址 0 是广播
2. RTU 不响应广播（理论上），但部分 RTU 误处理
4. 多 RTU 网络必须每个有唯一公共地址
5. 出厂默认公共地址通常非 0，但重置后可能变 0
```

## 案例 14：时钟同步后变位时间错

### 现象

主站发时钟同步 C_CS_NA_1 后，RTU 后续 M_SP_TB_1 变位事件时间全错（与实际差 1 小时）。

### 抓包

```text
主站：C_CS_NA_1 CP56 = 24 10 25 12 08 30 22    # 2024-10-25 12:08:30 (UTC? local?)
RTU → M_SP_TB_1 + CP56 = 24 10 25 13 08 30 22  # 1 小时后
```

### 定位

时区问题。主站发的是 UTC，RTU 当作本地时间（+8 时区）。

### 修复

主站发 CP56 时显式带 UTC 偏移。

### 复盘

```text
1. IEC 104 时钟同步通常是 UTC
2. RTU 端必须明确时区处理
4. 国内实践：RTU 通常按本地时间（UTC+8），主站需要适配
5. CP56 不带时区字段，必须主站 / RTU 约定
```

## 案例 16：文件传输失败

### 现象

主站发 ASDU 122 文件就绪，RTU 回 ASDU 123 文件准备好。但后续 ASDU 124 文件段传输失败。

### 抓包

```text
主站：ASDU 122 + 文件 ID
RTU：ASDU 123 + 文件大小
主站：ASDU 124 + 文件段 1
（RTU 不响应）
```

### 定位

RTU 文件传输超时设置过短，或主站段大小超出 RTU 限制。

### 修复

主站缩小段大小（如 64 字节），增加 RTU 超时。

### 复盘

```text
1. IEC 104 文件传输是分段的
2. 段大小通常 64-1500 字节协商
3. 超时设置要宽松
4. 关键文件（ICD/SCD）传输失败会导致配置丢失
```

## 案例 17：GI 启动后变位数据丢失

### 现象

主站发总召唤，RTU 回所有静态数据。但变位数据被丢弃。

### 抓包

```text
主站：C_IC_NA_1
RTU：M_SP_NA_1（静态）+ C_IC_NA_1 激活结束
（变位事件漏报）
```

### 定位

总召唤期间 RTU 突发被阻塞。

### 修复

RTU 端总召唤与突发分别排队：

```c
/* RTU 端优先级 */
if (gi_running) {
    enqueue_static_data();    // 总召唤响应
} else {
    if (event_pending) {
        send_spontaneous();    // 突发
    }
}
```

### 复盘

```text
1. 总召唤期间突发上传策略需 RTU 设计
2. 严格 RTU 阻塞突发会导致数据丢失
3. 工程实践：总召唤 + 突发并行（不阻塞）
4. 测试用例必须覆盖"总召唤 + 同时突发"
```

## 案例 18：多主站连接冲突

### 现象

两个主站连接到同一 RTU，RTU 数据冲突。

### 抓包

```text
主站 A → RTU：STARTDT_ACT
主站 B → RTU：STARTDT_ACT（同时）
（RTU 收到冲突命令）
```

### 定位

RTU 仅支持单主站。两个主站同时连导致状态机错乱。

### 修复

```text
1. RTU 配置仅允许单主站连接
2. 多主站需前置机做代理
3. 网络拓扑必须规划（一个 RTU 一个主站）
```

### 复盘

```text
1. IEC 104 标准支持多主站，但 RTU 实现通常仅单主站
2. 多主站必须 RTU 实现支持
3. 工程实践：前置机代理多主站
4. 网络 NAT / 防火墙不能 NAT 出多个连接
```

## 案例 19：S 帧间隔过长导致 RTU 误判

### 现象

RTU 收 I 帧但主站不发 S 帧确认，RTU 达到 w 限速后停止发送。

### 抓包

```text
主站 → RTU：I 帧 1（无 S 帧确认）
主站 → RTU：I 帧 2（无 S 帧确认）
...（连续 10 个 I 帧无 S 帧）
RTU：停止发送（达到 w）
```

### 定位

主站 S 帧发送逻辑错误，未实现每 w 个 I 帧发一次 S 帧。

### 修复

```c
/* 主站实现 */
void on_recv_i_frame() {
    recv_count++;
    last_nr = decode_nr(recv_buf);
    if (recv_count >= w) {
        send_s_frame(last_nr);  // S 帧确认
        recv_count = 0;
    }
}
```

### 复盘

```text
1. IEC 104 S 帧是接收确认，主站必须实现
2. S 帧间隔 = w 个 I 帧
3. 主站不发 S 帧 → RTU w 限速 → 链路阻塞
4. 测试用例必须验证 S 帧间隔
```

## 案例 20：时区与时钟回退导致数据混乱

### 现象

夏令时切换日（夏令时回退 1 小时），RTU 后续变位时间错。

### 抓包

```text
夏令时切换日：
  02:00 → 01:00（回退）
RTU 上报：
  M_SP_TB_1 CP56 = ... 01:30 ...   # 但实际应该是 02:30
```

### 定位

夏令时切换 + RTU 不支持夏令时。

### 修复

```c
/* RTU 端 */
if (dst_flag) {
    // 夏令时切换日特殊处理
}
```

或关闭夏令时（按 UTC 时间统一处理）。

### 复盘

```text
1. 夏令时切换是系统性问题
2. 国内 1992 年后已不用夏令时，但部分国家还在用
3. IEC 104 CP56Time2a 有夏令时标志
4. 工程实践：所有时间统一 UTC，避免夏令时混乱
```
